# UI Testing Runbook (Vorflux)

This runbook documents the end-to-end Vorflux flow for running the muesli-ios
XCUITest suite (`MuesliUITests`). It has two paths:

- **Path 1 (primary, authoritative gate):** run the XCUITest suite on the
  Vorflux CodeBuild macOS fleet via `xcodebuild test`, producing a `.xcresult`
  bundle. This is the only path that actually executes the XCUITest bundle and
  the only path that reaches the `--muesli-ui-testing*` fixture states.
- **Path 2 (optional, supplementary visual check):** build the shipping
  Release `.app` and boot it on Appetize, driven by the Appetize JavaScript
  SDK for screenshots. Appetize CANNOT run an XCTest bundle and can only show
  the default/real app state.

Muesli values used throughout:

| Field         | Value                          |
| ------------- | ------------------------------ |
| App name      | `Muesli`                       |
| Scheme        | `Muesli`                       |
| Project       | `MuesliiOS.xcodeproj` (generated by `xcodegen generate`; NOT checked in) |
| Bundle id     | `com.phequals7.muesli.ios`     |
| uitest buildspec   | `scripts/ci/uitest-buildspec.yml`   |
| appetize buildspec | `scripts/ci/appetize-buildspec.yml` |
| uitest artifact    | `MuesliUITests.xcresult.zip` (+ `MuesliUITests-deny.xcresult.zip`) |
| appetize artifact  | `Muesli.app.zip`               |

## Path 1 - Run the XCUITest suite on CodeBuild (primary automated path)

### Step 1: Zip the source on the Linux sandbox

The Vorflux sandbox is Linux and has no Xcode. Ship the committed source; the
`.xcodeproj` is regenerated remotely by `xcodegen generate` inside the
buildspec.

```bash
cd /code/muesli-ios
zip -r /var/tmp/muesli-src.zip . \
  -x ".git/*" ".git" \
  -x "build/*" "build" \
  -x "DerivedData/*" "DerivedData" \
  -x "*.xcodeproj/*"
```

Why these exclusions:

- `.xcodeproj` is excluded because it is regenerated remotely by
  `xcodegen generate` from `project.yml`. Shipping a locally generated project
  risks a stale/mismatched project; the buildspec always regenerates it.
- `.git`, `build`, and `DerivedData` are VCS/build junk that only bloat the
  upload.

What IS included (and is required by the remote build):

- `project.yml` (the XcodeGen manifest the remote `xcodegen generate` reads)
- `Muesli/` (app sources)
- `Shared/` (shared code, including `AppConstants.swift` launch-arg constants)
- `LiveActivityShared/`
- `MuesliKeyboard/` (keyboard extension target)
- `MuesliLiveActivityExtension/` (live activity extension target)
- `Tests/` (including the `MuesliUITests` XCUITest target)
- `scripts/` (including `scripts/ci/` buildspecs)

If `zip` is missing on the sandbox: `sudo apt-get install -y zip`.

### Step 2: Get an upload URL + build id

```
vflux_exec(command="ios-build upload-url")
```

Returns:

```json
{ "upload_url": "<PUT url>", "build_id": "<id>" }
```

### Step 3: Upload the zip

```bash
curl -XPUT -T /var/tmp/muesli-src.zip "<upload_url>"
```

### Step 4: Start the CodeBuild run with the uitest buildspec

```
vflux_exec(command="ios-build start --build-id '<build_id>' --app-name 'Muesli' --scheme 'Muesli' --buildspec-file scripts/ci/uitest-buildspec.yml")
```

Returns:

```json
{ "codebuild_build_id": "<full id>" }
```

No `--configuration` is passed: the scheme's Test action uses the Debug
configuration, which is what the `#if DEBUG`-gated fixtures require. (Forcing
Release would compile the fixtures out.)

### Step 5: Poll status until terminal

Poll roughly every 30 seconds until the status is terminal
(`SUCCEEDED`, `FAILED`, `FAULT`, `STOPPED`, or `TIMED_OUT`):

```
vflux_exec(command="ios-build status --codebuild-build-id '<codebuild_build_id>'")
```

### Step 6: Fetch logs

On failure, or to read the test-summary tail:

```
vflux_exec(command="ios-build logs --codebuild-build-id '<codebuild_build_id>' --tail-lines 200")
```

### Step 7: Download the .xcresult and inspect per-test results

```
vflux_exec(command="ios-build artifact-url --build-id '<build_id>' --artifact-name 'MuesliUITests.xcresult.zip'")
```

Returns:

```json
{ "download_url": "<GET url>" }
```

Then download and unzip:

```bash
curl "<download_url>" -o /var/tmp/MuesliUITests.xcresult.zip
unzip -o /var/tmp/MuesliUITests.xcresult.zip -d /var/tmp/xcresult
# On a Mac: xcrun xcresulttool get --path /var/tmp/xcresult/MuesliUITests.xcresult ...
```

Interpreting the result:

- The `.xcresult` bundle is the **authoritative per-test record**. Green means
  the flows pass on the CodeBuild macOS fleet.
- CodeBuild status `SUCCEEDED` implies the buildspec fail-gate passed, i.e. all
  tests were green.
- CodeBuild status `FAILED` with a produced `.xcresult` artifact means a red
  suite: triage the failing method(s) from the `.xcresult` and the logs, fix,
  and re-run.

### Secondary artifact: the pre-grant-free deny run

The uitest buildspec runs the onboarding mic-deny test FIRST, in its own
pre-grant-free `xcodebuild test` invocation (before the microphone is granted
to the simulator), so the deny branch is exercised in the default
unauthorized state. That invocation writes its own result bundle, downloadable
as the secondary artifact:

```
vflux_exec(command="ios-build artifact-url --build-id '<build_id>' --artifact-name 'MuesliUITests-deny.xcresult.zip'")
```

Both `.xcresult` bundles are zipped before the pass/fail gate, so both are
always downloadable and triageable even on a red run.

## Path 2 - Appetize visual/interactive check (optional, supplementary)

Appetize boots the shipping Release `.app` and is driven by its JavaScript SDK
for screenshots. It is a supplementary default-state visual check, never the
correctness gate.

### Step 1: Build the Release .app.zip

Reuse the same zip + upload steps as Path 1 (Steps 1-3), but request a fresh
`build_id` from `ios-build upload-url` and upload the same source zip. Then
start the appetize buildspec:

```
vflux_exec(command="ios-build start --build-id '<build_id>' --app-name 'Muesli' --scheme 'Muesli' --configuration 'Release' --buildspec-file scripts/ci/appetize-buildspec.yml")
```

`--configuration 'Release'` is required: Appetize requires a Release,
signing-disabled simulator build (a Debug build can crash on Appetize via its
`.debug.dylib`).

### Step 2: Poll status, then upload to Appetize

Poll `ios-build status` as in Path 1 Step 5 until `SUCCEEDED`, then:

```
vflux_exec(command="ios-build appetize-upload --build-id '<build_id>' --artifact-name 'Muesli.app.zip' --platform ios")
```

Returns:

```json
{ "embed_url": "...", "...": "..." }
```

### Step 3: Drive via the Appetize JS SDK

Host an HTML page with the `embed_url` (optionally append
`&screenOnly=true&toolbar=false`), serve it locally, open it in Chromium, and
drive the session in ONE continuous script:

```js
const client = await window.appetize.getClient("#appetize");
const session = await client.startSession({ debug: true });
await session.tap({ /* element | coordinates */ });
await session.type("some text");
await session.screenshot();
```

Save screenshots to `/code/.generated_artifacts/images/`. Keep all
interaction (init -> tap -> screenshot -> ...) in a single script run: Appetize
sandbox sessions auto-expire after a short idle period, so splitting steps
across separate script invocations can hit a dead session.

## XCUITest on CodeBuild vs Appetize is JS-SDK visual-only

These are two distinct, non-interchangeable capabilities. Read this before
assuming Appetize can substitute for the CodeBuild run.

- **Executing the XCUITest suite = CodeBuild `xcodebuild test`.** XCUITest
  bundles (`.xctest` targets) run ONLY via
  `xcodebuild test -destination 'platform=iOS Simulator,id=<udid>'` on a real
  macOS machine (the CodeBuild fleet). This compiles and launches the
  `MuesliUITests` runner against a booted simulator and produces the
  `MuesliUITests.xcresult` correctness gate. Every fixture test and every
  best-effort real-record test runs here.

- **Appetize = JS-SDK visual verification only.** Appetize boots the shipping
  `.app` in a cloud simulator and is driven only by its JavaScript SDK
  (`session.tap`, `session.type`, `session.screenshot`). Appetize CANNOT
  execute an XCTest/XCUITest bundle - there is no test runner; it drives the
  shipping app UI like a user.

- **Appetize cannot reach fixture states.** Critically, Appetize has no
  documented way to pass `--muesli-ui-testing*` process launch arguments to
  the booted app. The app's deterministic fixture states
  (`--muesli-ui-testing-onboarding`, `--muesli-ui-testing-completed-dictation`,
  `--muesli-ui-testing-dictionary-entries`, etc.) are triggered only by
  `ProcessInfo.processInfo.arguments`. So Appetize can show ONLY the
  DEFAULT/real fresh-install state (real onboarding, empty history, real record
  permission prompt) - never a seeded fixture state.

- **Conclusion.** Appetize is a supplementary default-state visual check built
  from a Release `.app`; it is never the automated correctness gate.
  Fixture-state Appetize screenshots (which would need a Debug build and a
  launch-argument mechanism Appetize does not document) are an out-of-scope
  follow-up. The authoritative gate is a `SUCCEEDED` CodeBuild run of
  `scripts/ci/uitest-buildspec.yml` plus the downloaded `.xcresult` showing the
  expected methods green.

## Relationship to existing GitHub CI

The existing `.github/workflows/ci.yml` already gates every PR and every push
to `main` on `macos-latest`
(`brew install xcodegen` -> `xcodegen generate` -> build ->
`xcodebuild test -project MuesliiOS.xcodeproj -scheme Muesli ... CODE_SIGNING_ALLOWED=NO`),
running the full `MuesliUITests` + `MuesliTests` suite. **It is left
unchanged.** It is the always-on per-PR correctness signal.

Vorflux CodeBuild (this runbook) is the on-demand / cloud path on the same
macOS-fleet toolchain: used during plan execution and any time a run is
triggered without waiting on GitHub Actions, producing a downloadable
`.xcresult`. It complements GitHub CI; it does not replace or supersede it.

Note: GitHub CI runs against a discovered simulator WITHOUT the
`xcrun simctl privacy <udid> grant microphone com.phequals7.muesli.ios`
pre-grant step that the uitest buildspec performs. The real-record tests are
written to tolerate deny, so GitHub CI stays green either way. If GitHub CI
should also exercise the recording branch, add the same mic pre-grant step
before its test step (not part of this plan).
